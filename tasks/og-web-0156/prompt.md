# Save and restore game menu preferences

Restore preference persistence in the supplied browser game menu and rebuild the settings layout from `assets/game_menu_reference.png`. The reference shows only the upper portion of the menu; its remaining action rows and buttons must also be accessible.

- **R1 — Preference object.** Implement `Preferences.load()` and `save()` in `preferences.js`, using the supplied local storage key `webgame.userPreferences`. Store music value, SFX value, input type index and a dictionary mapping actions to remapped keyboard events. With no saved data, default to music 0, SFX 1, input type 0 and the supplied default keys. Preserve serializable `code` and `key` fields for events.
- **R2 — Restore visible controls.** Implement `mountMenu(root, services)` in `menu.js`. On each menu creation, load saved values and apply them to the unique `MusicSlider`, `SFXSlider` and `InputTypeButton` controls. Both sliders range from 0 to 1 with step 0.05; input options are Keyboard then Gamepad at indices 0 and 1. Also update the supplied audio and input-type services, rather than only changing control text.
- **R3 — Save immediately.** Every music/SFX slider input event and every input-type change must immediately save the new complete preferences, without a confirmation button. Preserve other fields and existing remaps. Recreating the menu or refreshing the page must restore them.
- **R4 — Remapping.** Retain five action/button rows in this order: `move_forward`, `move_backward`, `turn_left`, `turn_right`, `weapon_fire`. Apply a saved event back to the actual input map before creating its button. In `remap.js`, make `RemapButton.completed(event)` emit `remapped` with `action` and `event` in its detail. The menu immediately updates the dictionary and saves on completion. Buttons display the restored keys; keep the provided key capture and real action handling operational.
- **R5 — Reference layout.** In `style.css`, restore the reference's dark background, light 16-pixel text, two columns with labels on the left and controls on the right, Continue Game above, and Return to menu and Quit Game below. At width 960, the menu starts 256 pixels from the left and 360 from the top; the control column begins near 398, with rows approximately 32 pixels high. Continue the cropped layout downward so all five action rows and buttons are available, allowing page scrolling. Reduce margins on narrow screens to prevent horizontal control overflow. Do not use the reference image as a substitute for an interactive menu.
- **R6 — Lifecycle and play.** `dispose()` removes this menu's control and remap listeners, preventing duplicate handling after recreation. Preserve the provided recreate, clear-saved-settings, audio-test and continue-game controls. After remapping forward to I, recreate the menu and continue playing: I must drive the actual actor and the former W must no longer move it forward. Other preferences must remain intact.

Edit `preferences.js`, `menu.js`, `remap.js` and `style.css`; keep other supplied files unchanged. Submit the complete browser package with `index.html` as entry. Acceptance uses the original example of music 0.35, SFX 0.65, input type 1 and forward key I, plus other values, actual input after recreation, independent saves, listener cleanup and visible control layout/state.
